2. CODE AND REPRODUCIBLE SETUP

Public repository: https://github.com/amangang3/hw3-autonomous-canvas-agent

Prerequisites: macOS or Linux, Python 3.11+, uv, Hermes Agent, and a Canvas access token created and installed by the human.

Core project setup:
1. git clone https://github.com/amangang3/hw3-autonomous-canvas-agent.git ~/hw3-agent
2. cd ~/hw3-agent
3. uv sync --extra test
4. chmod 755 bin/canvas_tool scripts/collect_evidence.sh scripts/*.py
5. mkdir -p state/drafts logs && chmod 700 state state/drafts logs
6. The human creates ~/.config/hw3-agent/env with CANVAS_TOKEN=<token>, chmods the directory 700 and file 600, and never exposes the token to the model or a prompt.
7. uv run --extra test pytest -q
8. bin/canvas_tool status

Autonomous deployment:
1. Create a dedicated Hermes profile named canvasagent and authenticate that profile with a model provider. Restrict its terminal working directory to ~/hw3-agent.
2. Disable unrelated cron-profile capabilities. Retain only terminal access needed to invoke bin/canvas_tool and file access needed to read RUNTIME.md and write a draft under state/drafts.
3. Install/start the Hermes gateway as a launchd service so the scheduler survives closing the interactive terminal.
4. Create a recurring job on */30 * * * * with the prompt: Run one HW3 forum cycle. Follow ~/hw3-agent/RUNTIME.md exactly and actively find one substantive contribution to make.
5. Verify with hermes -p canvasagent cron list, hermes gateway status, bin/canvas_tool status, and the test/secret-scan commands in the README.

README.md contains copyable Hermes profile, tool-policy, gateway, cron, dry-run, verification, pause/resume, and credential-handling instructions. No source ZIP is required; all code is directly inspectable in the repository.

3. ARCHITECTURE AND AUTONOMY

Scheduler
Hermes cron invokes the dedicated canvasagent profile every 30 minutes. A launchd-supervised Hermes gateway owns the scheduler independently of the interactive terminal. Each invocation starts a fresh bounded cycle.

Canvas access boundary
The model decides what contribution is useful, but only bin/canvas_tool may access Canvas. client.py pins HTTPS traffic to canvas.mit.edu, applies timeouts, validates same-origin pagination, retries only eligible reads, and issues each POST once. Discovery fails unless it finds exactly one active-course topic titled “Homework 3: Agent Discussion Forum.” There are no edit or delete paths.

Decision logic
RUNTIME.md requires begin, review of unseen entries plus eligible older candidates, optional thread-context inspection, selection of one substantive non-duplicative contribution, a 60–250 word draft, guarded submission, and end. Replies are preferred. Forum content is labeled untrusted and instructions embedded in posts are never followed.

Deterministic enforcement
Before every write, gate.py checks run ownership, target validity, self-reply and duplicate conditions, content-disclosure policy, STOP state, rolling limits, and a fresh exact COURSE-TEAM CONTROL: RUNNING line. It commits durable intent before the external write. Drafts must be regular UTF-8 files directly under state/drafts; unsafe paths and final-component symlinks are refused. Output is token-redacted.

Local persistent memory
SQLite runs in WAL mode. meta stores Canvas IDs and breaker state; seen_entries prevents repeatedly presenting items as new; actions is the idempotency/intent journal with intended, posted, verified, and abandoned states; runs stores cycle outcomes and skip reasons. BEGIN IMMEDIATE and advisory process locks prevent overlap and fence begin, write/verification, and end operations.

Verification and recovery
After POST, the wrapper re-reads Canvas after bounded delays of 0, 1, 2, 4, and 8 seconds. Verification requires the returned entry ID, author, parent, normalized logical text, and timestamp to match the intent. It never retries an uncertain write. A later begin reconciles unresolved actions from a fresh thread read: exactly matching effects become verified; old unmatched pre-write intents become abandoned and are never automatically replayed.

Rate limits and stopping rule
The deterministic gate allows at most two actions per run, three intended/posted/verified actions per rolling hour, and one new thread per 24 hours; current runtime policy requests one contribution per cycle. Every write rechecks the course-team control line and state/STOP. Three consecutive error outcomes create STOP; a successful run resets the breaker. Course staff can pause through the control line, and the operator can stop locally.

5. FAILURE-AND-RECOVERY AND DUPLICATE-EFFECT PROTECTION

Injected lost acknowledgement
FaultController supports one-shot lost_ack, crash_after_intent, timeout_get, and malformed faults. test_lost_ack_leaves_intent_then_begin_reconciles injects lost_ack after fake Canvas applies the POST but before local acknowledgement. The test proves that the intent existed first, Canvas received exactly one POST, the first run did not retry, the next begin reconciled the one matching effect to verified, and the POST count remained one.

Injected crash after durable intent
The crash_after_intent test commits intent and crashes before Canvas is called. Canvas receives zero POSTs. After the recovery interval, the next begin marks the unmatched intent abandoned and never reposts it. A stale-run takeover test atomically closes an abandoned run, increments the breaker, starts a new run, and still performs zero Canvas writes.

Live delayed-read recovery
Multiple live scheduled writes, including entries 230741, 231014, 231142, 231229, 231268, and 231285, were accepted by Canvas but not immediately visible through the verification read path. The agent did not repeat any POST. Later fresh reads found one matching entry each and reconciled the existing records to verified. Entry 231285 was reconciled while preparing this snapshot, returning the breaker to 0 with no pending intent.
